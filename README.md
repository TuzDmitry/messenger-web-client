# Messenger Web Client

Веб-клиент для отправки и получения текстовых сообщений через [GREEN-API](https://green-api.com/). Внешний вид — по мотивам [web.max.ru](https://web.max.ru/).

Проверено на Telegram-инстансе. Методы и формат уведомлений GREEN-API для MAX идентичны — приложение работает с инстансом любого из этих мессенджеров.

**Сценарий:** ввести `idInstance` и `apiTokenInstance` → создать чат по номеру телефона → отправить сообщение → ответ собеседника появляется в чате.

## Запуск

Нужен Node.js 20.19+.

```bash
npm install
npm run dev
```

Приложение откроется на http://localhost:5173. Бэкенд не нужен: клиент ходит в GREEN-API напрямую (CORS разрешён).

| Команда             | Что делает                        |
| ------------------- | --------------------------------- |
| `npm run dev`       | dev-сервер                        |
| `npm run build`     | проверка типов и сборка в `dist/` |
| `npm run preview`   | локальный просмотр сборки         |
| `npm test`          | тесты (Vitest)                    |
| `npm run lint`      | oxlint                            |
| `npm run typecheck` | `tsc -b`                          |
| `npm run format`    | Prettier                          |

## Где взять учётные данные

1. Зарегистрироваться в [личном кабинете GREEN-API](https://console.green-api.com) и создать инстанс (тариф «Разработчик» бесплатный).
2. Авторизовать инстанс: привязать аккаунт мессенджера по QR-коду или коду из кабинета.
3. Скопировать `idInstance` и `apiTokenInstance` со страницы инстанса.
4. Если у инстанса персональный `apiUrl` и общий `https://api.green-api.com` не отвечает — указать его в блоке «Дополнительно» на экране входа.

Получение сообщений работает через очередь уведомлений, поэтому в настройках инстанса должны быть включены входящие и исходящие с телефона уведомления, а `webhookUrl` — пустым. Если уведомления выключены, приложение покажет плашку с кнопкой «Включить».

## Деплой

Сборка — статика. На Vercel: импортировать репозиторий, пресет Vite определится сам (`npm run build`, каталог `dist`). Роутера нет, поэтому rewrites не нужны.

## Архитектура

```
src/
  api/          HTTP-клиент, методы GREEN-API, zod-схемы ответов и уведомлений, фикстуры
  store/        Zustand: сессия, чаты и сообщения, состояние соединения
  features/
    auth/       вход с проверкой через getStateInstance, выход
    chats/      список чатов, новый чат по номеру через checkAccount
    messages/   лента, поле ввода, оптимистичная отправка с повтором
    polling/    цикл получения, одна вкладка-поллер (Web Locks)
    settings/   проверка и включение уведомлений инстанса
  layout/       трёхколоночный каркас, на телефоне — одна колонка
  ui/           базовые компоненты: кнопка, поле, модалка на <dialog>, аватар
  i18n/         все строки интерфейса
  lib/          нормализация номера, время, локальные id
```

Стек: React 19, TypeScript (strict), Vite, Zustand, zod, CSS Modules. Тесты: Vitest, Testing Library.

## Ключевые решения

- **Получение — HTTP API (long polling), не вебхуки.** Так требует ТЗ, а вебхукам нужен публичный бэкенд. Цикл: `receiveNotification` (20 с) → обработать → `deleteNotification`. Удаляются уведомления любого типа, даже нераспознанные, — иначе одно битое навсегда заблокирует очередь. При ошибках — бэкофф 1 → 30 с, при 401/403 — выход с объяснением.
- **Номер → `chatId` через `checkAccount`.** Входящие приходят с `chatId`, без него ответ не сопоставить с чатом. Номер нормализуется до цифр, страновых ограничений на клиенте нет — их проверяет API.
- **Дедупликация по `idMessage`.** Если `deleteNotification` не прошёл, уведомление придёт снова и не задублится. `receiptId` для этого не годится: после очистки очереди нумерация начинается заново.
- **Оптимистичная отправка.** Сообщение сразу появляется в ленте, затем получает статус «отправлено» или «не отправлено» с кнопкой повтора. После перезагрузки неподтверждённые помечаются как неотправленные — автоповтор мог бы дать дубль у получателя.
- **Одна вкладка получает сообщения.** Очередь у инстанса одна: две вкладки делили бы её, и ответ появился бы только в одной. Через Web Locks очередь читает одна вкладка, остальные показывают «Открыть здесь».
- **Без TanStack Query.** Очередь требует строгого порядка receive → handle → delete, а не кэша с повторными запросами; мутация одна. Состояние — в Zustand, доступном поллеру вне React.
- **Без UI-библиотеки.** Компонентов немного, а MUI/Ant пришлось бы перебивать под стиль MAX. Модалки — нативный `<dialog>`.
- **Ответы API — `unknown` и проверяются zod.** Схемы нестрогие: лишние поля в реальных ответах не ломают разбор.
- **Учётные данные и чаты — в `sessionStorage`.** Переживают F5, удаляются вместе с вкладкой и при выходе.

## Тесты

Unit-тесты на api-слой, разбор уведомлений, стор, поллер (порядок receive/delete, бэкофф, 408, 401) и Web Locks. Интеграционный тест (`src/App.test.tsx`) проходит сценарий из ТЗ целиком на фейковом GREEN-API: `fetch` подменён, очередь уведомлений настоящая. Фикстуры — реальные обезличенные ответы API.

## Ограничения

- Токен инстанса хранится в браузере. В продакшене запросы стоит проксировать через свой бэкенд.
- История переписки с сервера не загружается: в чате видны сообщения с момента входа.
- Только текст и личные чаты; медиа, группы, статусы доставки и прочтения не поддерживаются.
- Получатель — только номер телефона, без `@username` (он есть только в Telegram).
- Ленты в разных вкладках не синхронизируются: сообщения получает и отправляет одна вкладка.
- Не проверено, находит ли `checkAccount` пользователя Telegram, скрывшего номер настройками приватности.
